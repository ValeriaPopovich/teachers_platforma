# Teachers Platform — спецификация рефакторинга

**Статус:** принято к реализации  
**Версия:** 2.0  
**Дата:** 2026-08-09  
**Область:** существующий frontend, локальные данные, авторизация и синхронизация Supabase

Этот документ заменяет первоначальный расширенный план рефакторинга. Он содержит только работу, необходимую для безопасного развития текущего продукта. Архитектурные решения и причины их принятия находятся в [`docs/adr`](./adr/README.md).

## 1. Результат рефакторинга

После завершения работ пользователь не должен заметить изменения в сценариях и расчётах. Для разработчика результат должен быть следующим:

- код разделён на содержательные модули;
- локальные данные имеют явную привязку к единственному аккаунту устройства;
- загрузка, миграция, сохранение и синхронизация имеют явные границы;
- отображение интерфейса не изменяет persisted state;
- финансовые правила, расписание и импорт тестируются без DOM;
- старые резервные копии продолжают импортироваться;
- облачный конфликт не приводит к молчаливой перезаписи более новых данных;
- каждый этап можно откатить отдельно.

Рефакторинг не должен менять дизайн, пользовательские сценарии или бизнес-правила. Обнаруженную ошибку поведения исправлять отдельным небольшим изменением с отдельным тестом.

## 2. Текущее состояние и главные риски

Приложение находится в одном `index.html` размером около 195 KB. В нём совмещены разметка, CSS, авторизация, состояние, расчёты, DOM-rendering, `localStorage`, Supabase и импорт backup.

Приоритеты определяются не размером файла, а риском потери или смешивания пользовательских данных.

> **Важно про базу отсчёта.** Этот раздел описывает состояние ветки `main`. Часть рисков уже устранена в рабочей ветке в рамках Этапа 0 — фактический статус указан в каждом подпункте и в [разделе Этапа 0](#этап-0--немедленная-защита-данных).

### 2.1. Неявный владелец локальных данных

По продуктовой модели один browser profile используется только одним аккаунтом. Поэтому отдельные localStorage keys для нескольких пользователей и UI переключения аккаунтов не нужны.

При этом на `main` ключ `tutorCabinet_v1` не содержит даже защитной отметки владельца. Достаточно сохранить один owner marker рядом с локальными данными и запрещать cloud upload при неожиданном несовпадении с текущим пользователем.

**Статус:** устранено на Этапе 0. Добавлен marker `tutorCabinet_owner_user_id`, upload проходит через guard `canUploadLocalState`; при входе второго аккаунта без облачных данных отправка чужой локальной копии блокируется.

### 2.2. Изменение данных во время render

На `main` `renderAll()` вызывает функции, которые:

- удаляют старые события (`pruneOldHistory`);
- удаляют orphan-записи (`sweepOrphans`);
- меняют статусы прошедших занятий (`normalizePastLessons`);
- обновляют финансовые поля будущих занятий (`syncFutureGroupBilling`);
- записывают результат в `localStorage`.

Отображение интерфейса не должно молча удалять или изменять persisted state.

**Статус:** частично устранено на Этапе 0. `renderAll()` больше не вызывает эти функции. При этом полного решения инварианта ещё нет:

- `normalizePastLessons` и `syncFutureGroupBilling` не удалены, а перенесены в bootstrap и в интервал `checkAlerts` (раз в 60 сек) и по-прежнему молча пишут в `localStorage`. Это осознанный промежуточный шаг: превращение их в именованные maintenance operations с точными правилами — задача Этапа 3.
- `sweepOrphans` и `pruneOldHistory` сейчас не вызываются нигде (мёртвый код). Как следствие, orphan-записи больше не подчищаются автоматически — это изменение поведения относительно `main`. Допустимо до формализации правил на Этапе 3; тогда функции либо оживают как maintenance operation, либо удаляются.

### 2.3. Неатомарная cloud sync

На `main` cloud save выполняет `upsert` полного JSON, а сохранение триггерится через monkey patch `Storage.prototype.setItem`. Debounce не исключает параллельные запросы, а `last-write-wins` может затереть изменения другого устройства или вкладки.

**Статус:** частично устранено на Этапе 0. Monkey patch убран (save идёт только через persistence API), сохранения сериализованы клиентской очередью `saveChain` (одновременно не больше одного запроса). **Не сделано:** серверный atomic compare-and-swap по `revision` — конфликт между устройствами всё ещё не обнаруживается. Это задача Этапа 5.

### 2.4. Неполная проверка backup

Текущая проверка импорта не гарантирует ссылочную целостность всех сущностей. При merge не remap-ится `payment.lessonId` (подтверждено в коде рабочей ветки: студенты/группы/занятия remap-ятся, а `payment.lessonId` — нет). Replace import выполняется без recovery copy.

**Статус:** не исправлено. Запланировано на Этап 4.3 (backup validation/merge вместе с тестами). Вне рамок Этапа 0.

### 2.5. Непроверенные бизнес-расчёты

Финансы, расписание и автоматические изменения занятий связаны с DOM и общим mutable state. Их нельзя безопасно переносить без зафиксированных входных данных и ожидаемых результатов.

## 4. Границы текущей работы

**Принцип пропорциональности.** Это соло-проект на один `index.html`, на GitHub Pages, с одним аккаунтом на устройство. Единственное, ради чего рефакторинг обязателен, — не потерять и не смешать пользовательские данные. Всё, что не защищает данные напрямую, делается в минимально достаточном виде. Абстракция вводится только когда она уже окупается на текущем объёме, а не «на будущее». Полные версии тяжёлых механизмов (см. ниже) полезны, но не сейчас — они оформляются отдельным ADR, когда появится измеримая причина.

### Входит в работу

- явная привязка локальных данных к аккаунту устройства;
- аудит RLS для текущих таблиц;
- baseline fixture и ожидаемые результаты;
- минимальная инфраструктура lint, format и tests;
- физическое разделение HTML, CSS и JavaScript;
- ES Modules без обязательного bundler;
- централизованный state и local persistence;
- versioned schema, validation и migrations;
- выделение финансов, расписания и backup/import в чистые модули;
- надёжная cloud sync с обнаружением конфликтов;
- минимальное разделение UI по страницам;
- исправление основных проблем keyboard/modal accessibility;
- CI и release checklist.

### Не входит в работу

- переход на React, Vue, Svelte или другой framework;
- изменение дизайна;
- изменение финансовых правил;
- новые продуктовые функции;
- нормализация JSON blob в набор Supabase-таблиц;
- dual-write старой и новой схемы БД;
- realtime collaboration;
- обязательный selective rendering всех страниц;
- runtime indexes и виртуализация списков без подтверждённой проблемы;
- полный E2E-набор для каждого второстепенного сценария;
- сложная repository-иерархия для каждой сущности;
- заранее заданное большое количество файлов и слоёв.

Эти пункты не являются скрытым backlog текущего рефакторинга. Если необходимость появится, она оформляется отдельной спецификацией и новым ADR.

### Делаем сейчас в минимальном виде (полное — потом)

Эти работы входят в скоуп, но сознательно ограничены. Полная версия каждой — не оверинжиниринг «в принципе», а просто преждевременна для текущего масштаба. Расширяем только по факту боли.

- **Store.** Сейчас: одна точка мутации state и правило «render не мутирует, persistence не рендерит». Не сейчас: механизм подписок (`subscribe`/listeners), пока чистый полный `renderAll()` не создаёт заметной проблемы. Полное — когда появится реальная нужда в точечных обновлениях UI.
- **Versioned state и migrations.** Сейчас: `schemaVersion: 1`, structural + referential validation, recovery copy. Не сейчас: фреймворк цепочки миграций между версиями — писать его под единственную версию нечего. Первую реальную миграцию добавляем, когда меняется data shape.
- **Cloud sync.** Сейчас: серверный atomic CAS по `revision` + видимый статус `conflict` + одна последовательная save-очередь (уже есть). Не сейчас: сложные retry/backoff-стратегии, offline-очередь из нескольких snapshot'ов, автоматический merge. Достаточно: не терять более новую версию молча и дать пользователю выбор при конфликте.
- **Тесты.** Сейчас: Vitest на финансы, расписание, backup + ручной smoke-чеклист. Не сейчас: обязательный Playwright/E2E в CI — для соло-проекта его поддержка дороже пользы. Браузерный автосмок добавляем точечно и только если он стабилен.
- **CI.** Сейчас: CI гоняет lint и unit-тесты. Не сейчас: жёсткий гейт «CI обязателен для merge» как процесс — для одного разработчика это церемония. Гейт вводим, если появятся другие контрибьюторы.
- **Accessibility.** Сейчас: сохранить уже работающие focus-trap и Escape в модалках, не сломать их при разделении файлов. Не сейчас: полный a11y-аудит — это не про потерю данных, доводим по возможности, не блокируя выпуск.
- **ADR.** Текущие решения зафиксированы; дробить их дальше не нужно. При желании 8 файлов можно свести в один `DECISIONS.md` — это косметика, не обязательна.

## 5. Инварианты данных

Эти правила нельзя нарушать ни одним этапом:

1. ID ученика уникален.
2. Участник группы ссылается на существующего ученика.
3. Занятие имеет корректного владельца: ученика или группу.
4. `payment.studentId` ссылается на существующего ученика.
5. `payment.lessonId`, если задан, ссылается на существующее занятие или обрабатывается документированным legacy-правилом.
6. Merge не создаёт ID collisions и remap-ит все ссылки.
7. Удаление ученика и группы выполняется одной явной domain-операцией.
8. Отмена и перенос занятия не создают двойное начисление.
9. Повторная генерация расписания не создаёт дубли.
10. Финансовый результат не зависит от порядка элементов в массивах.
11. Ошибка загрузки, миграции или импорта не перезаписывает последнюю валидную копию.
12. Cloud upload разрешён только если локальный owner marker отсутствует при первом legacy-запуске или совпадает с текущим `user.id`.

## 6. Порядок реализации

Тесты не являются отдельным поздним этапом. Каждый PR включает проверки для изменяемой ответственности.

### Этап 0 — немедленная защита данных

> **Статус реализации на 2026-08-09.** Задачи 2–8 выполнены в рабочей ветке. Задача 1 (RLS-аудит) выполнена частично — см. [`docs/SUPABASE_RLS_AUDIT.md`](./SUPABASE_RLS_AUDIT.md): анонимное чтение `app_data`/`profiles` закрыто (проверено REST-запросами), остаётся cross-user policy test с двумя авторизованными тестовыми пользователями. Хвост после ревью кода закрыт: `pushCloud` при непарсимом `raw` теперь возвращает `false` и показывает ошибку. Открытый хвост: `sweepOrphans`/`pruneOldHistory` остались мёртвым кодом (см. §2.2), решается на Этапе 3.

#### Задачи

1. Провести read-only аудит текущих RLS policy:
   - `app_data`: SELECT/INSERT/UPDATE только для `user_id = auth.uid()`;
   - `profiles`: пользователь читает только свой профиль;
   - проверить невозможность подменить `user_id`.
2. Сохранить существующий ключ `tutorCabinet_v1`: модель нескольких локальных аккаунтов не вводится.
3. Добавить отдельный owner marker, например `tutorCabinet_owner_user_id`.
4. До cloud upload сверять owner marker с текущим `user.id`.
5. Упростить legacy-переход:
   - если облако содержит данные, облачная версия заменяет локальную и marker получает текущий `user.id`;
   - если облако пусто, а marker отсутствует, существующие local data считаются данными единственного аккаунта устройства и используются как начальная cloud version;
   - после первого успешного cloud save marker получает текущий `user.id`;
   - если marker неожиданно не совпадает с текущим `user.id`, upload блокируется и показывается ошибка; отдельный multi-account migration flow не реализуется.
6. При logout завершить или отменить ожидающий save и очистить runtime-ссылки на session. Локальная копия остаётся для того же аккаунта.
7. Убрать monkey patch `Storage.prototype.setItem`; cloud save вызывается только через persistence API.
8. Временно отделить destructive cleanup от `renderAll()`; до формализации правил он не должен удалять записи молча.

RPC `email_exists` сохраняется как принятое продуктовое решение и не пересматривается в рамках рефакторинга.

#### Обязательные проверки

- существующий пользователь с cloud data получает облачную версию;
- при пустом облаке и отсутствии marker текущие legacy local data успешно становятся первой cloud version;
- искусственно созданное несовпадение marker и `user.id` блокирует upload;
- ошибка cloud save во время logout видна пользователю и не считается успехом;
- пользователь A не может прочитать или изменить строку пользователя B через Supabase API.

#### DoD

- [x] Существующий localStorage key сохранён и имеет owner marker.
- [x] Несовпадение owner marker блокирует cloud upload.
- [x] Нет override встроенных Storage API.
- [ ] RLS-аудит задокументирован.
- [x] `renderAll()` не выполняет молчаливое удаление orphan-записей и не меняет статусы/финансовые поля.
- [ ] Оставшиеся молчаливые мутации persisted state (`normalizePastLessons`, `syncFutureGroupBilling` в bootstrap/интервале) явно отмечены как временные и передаются в Этап 3 (см. §2.2).
- [ ] Отключение `sweepOrphans`/`pruneOldHistory` зафиксировано как осознанный trade-off до формализации на Этапе 3.

### Этап 1 — baseline и инженерная страховка

#### Fixture

Создать анонимизированный fixture текущего production-формата. Он должен включать:

- разовую оплату и абонемент;
- долг и аванс;
- групповые занятия с разными типами оплаты участников;
- завершённые, отменённые, перенесённые и будущие занятия;
- связанный с занятием платёж;
- регулярное расписание;
- архив финансов и тем;
- личное событие;
- legacy-поля, встречающиеся в реальных backup.

Для fixture сохранить отдельный manifest с ожидаемыми:

- количеством сущностей;
- балансом каждого ученика;
- числом купленных и использованных занятий;
- общей аналитикой за фиксированный период;
- количеством будущих занятий;
- результатом повторной генерации расписания.

#### Минимальная инфраструктура

- `package.json`;
- Vitest или эквивалент для unit tests — это основной инструмент, вся ценность здесь;
- ESLint;
- Prettier;
- GitHub Actions: install, lint, unit tests.
- Playwright/E2E — **опционально и не сейчас**. Критический smoke (ниже) выполняется как ручной чеклист. Браузерный автосмок добавляется точечно и только если он стабилен и реально экономит время (см. §4).

Критический smoke ниже — это ручной чеклист, а не набор автотестов. До выделения чистых функций baseline фиксируется этим чеклистом и manifest'ом. После выделения каждого domain-модуля соответствующая часть baseline сразу становится автоматическим unit-тестом.

#### Критический smoke

1. Вход существующего пользователя и reload session.
2. Создание и редактирование ученика.
3. Создание регулярного и разового занятия.
4. Завершение, отмена и перенос занятия.
5. Разовая оплата и абонемент.
6. Проверка баланса.
7. Backup export, replace import и merge import.
8. Cloud save и повторная загрузка.
9. Гейтинг доступа: заблокированный (`status !== 'active'`) и истёкший (`access_until` в прошлом) аккаунт видит экран ограничения и не попадает в кабинет — поведение не сломано рефактором.

#### DoD

- [ ] Fixture не содержит персональных данных реальных пользователей.
- [ ] Fixture импортируется текущей версией.
- [ ] Ожидаемые финансовые результаты зафиксированы числами.
- [ ] Есть повторяемый smoke checklist.
- [ ] Команды lint и tests задокументированы.

### Этап 2 — механическое разделение файлов

Цель этапа — уменьшить физический монолит без изменения поведения.

#### Порядок

1. Вынести CSS в небольшое число файлов: variables/theme, application styles, responsive. Более мелкое деление делать только при появлении самостоятельной ответственности.
2. Вынести два существующих IIFE в обычные внешние scripts без изменения порядка выполнения.
3. Проверить smoke и backup compatibility.
4. Отдельным изменением перейти на `type="module"`, явные import/export и strict module semantics.
5. Убрать bootstrap-патчи заранее известной HTML-разметки: нужные поля должны находиться в HTML изначально.

Переход на external scripts и переход на ES Modules не объединять с изменением бизнес-логики. ES Modules меняют время выполнения, область видимости и strict mode, поэтому это отдельная проверяемая операция.

#### Ограничения

- не менять storage keys, data shape и финансовые формулы на этом этапе;
- не переименовывать все функции ради единообразия;
- не создавать пустые слои и по одному файлу на каждую короткую функцию;
- не внедрять bundler, если GitHub Pages и тесты работают без него.

#### DoD

- [ ] `index.html` содержит shell и статическую разметку, а не основную логику.
- [ ] Нет крупного inline CSS и application JavaScript.
- [ ] Модули загружаются на GitHub Pages без недокументированного build step.
- [ ] Baseline и smoke не изменились.
- [ ] Старый backup импортируется.

### Этап 3 — state, validation и persistence

#### Обязательный pipeline загрузки

```text
raw storage/cloud/import
→ parse
→ structural validation
→ migration
→ referential validation
→ normalized application state
```

Только валидное состояние может стать активным.

#### State envelope

Новая persisted форма должна содержать как минимум:

```json
{
  "meta": {
    "schemaVersion": 1,
    "updatedAt": "ISO-8601"
  },
  "data": {
    "students": [],
    "groups": [],
    "lessons": [],
    "events": [],
    "payments": [],
    "financeArchive": {},
    "topicLog": {},
    "settings": {}
  }
}
```

Конкретное значение первой версии выбирается при реализации после описания текущей legacy-схемы.

#### Store

Достаточен минимальный API. Обязательны только первые три метода:

```js
store.getState();
store.update(actionName, mutator); // единственная точка мутации
store.replace(nextState);          // load/import/replace
store.subscribe(listener);         // опционально — вводить только когда понадобится
```

`subscribe` не является обязательным для этого этапа: пока полный `renderAll()` чист и не тормозит, persistence и render можно вызывать явно после `update`, без механизма подписок. Добавляем listeners только по факту нужды в точечных обновлениях (см. принцип пропорциональности в §4).

Требования:

- mutation выполняется только через store/domain action;
- после успешного изменения state вызывается local persistence (напрямую или через подписку — по ситуации);
- cloud sync получает подтверждённую snapshot через явный API;
- persistence не вызывает rendering;
- rendering не вызывает mutation или persistence;
- полный `renderAll()` допустим, если он чистый и не создаёт заметной проблемы производительности.

#### Maintenance operations

Автоматическое завершение прошедших занятий, retention событий и очистка orphan-записей становятся именованными операциями. Для каждой операции должны быть определены:

- момент запуска;
- точные правила;
- идемпотентность;
- лог/результат изменений;
- тест;
- поведение при ошибке.

Некорректные импортированные записи нельзя удалять как побочный эффект render.

#### DoD

- [ ] State имеет `schemaVersion` и проходит structural + referential validation.
- [ ] Pipeline загрузки поддерживает миграции, но сам набор миграций может быть пустым, пока версия одна (фреймворк цепочки версий не пишем заранее).
- [ ] Любая добавленная миграция идемпотентна.
- [ ] Ошибка не перезаписывает последнюю валидную копию.
- [ ] Нет прямых `localStorage.setItem` вне persistence/migration bootstrap.
- [ ] Render-функции не изменяют state.
- [ ] Legacy fixture успешно загружается с теми же результатами.

### Этап 4 — критичная domain-логика и backup

Модули извлекаются по одному. Перенос считается законченным только вместе с тестами старого поведения.

#### 4.1. Finances

Чистый модуль должен рассчитывать:

- начислено и оплачено;
- долг и аванс;
- разовую оплату;
- купленные, использованные и оставшиеся занятия абонемента;
- `paid_missed` и `not_charged`;
- влияние `billingSince` и `financeArchive`;
- групповые занятия с индивидуальным типом оплаты участников;
- аналитику за период.

Минимальные тесты:

1. Предоплата и оплата после занятия.
2. Неоплаченное занятие, долг и переплата.
3. Абонемент, его окончание и покупка следующего.
4. Пропуск со списанием и без списания.
5. Отмена и перенос.
6. Удаление связанного платежа.
7. Смена `billingSince` и legacy archive.
8. Групповое занятие с разными типами оплаты.
9. Повторный расчёт не создаёт платежи.

#### 4.2. Schedule and lessons

Чистые функции должны отвечать за:

- генерацию регулярных занятий;
- предотвращение дублей;
- конфликты времени;
- групповые series;
- перенос и отмену;
- local date/time boundaries;
- status transitions.

Повторный вызов с тем же состоянием должен быть идемпотентным.

#### 4.3. Backup/import

Export содержит:

- имя приложения;
- app version;
- schema version;
- exportedAt;
- данные.

Replace import выполняется атомарно:

1. parse;
2. проверить допустимый размер и структуру;
3. мигрировать;
4. проверить уникальность ID и ссылки;
5. создать recovery copy текущих данных;
6. только затем заменить state и запустить сохранение.

Merge remap-ит:

- student IDs;
- group IDs;
- lesson IDs;
- series IDs;
- `payment.studentId` и `payment.lessonId`;
- `lesson.movedFrom`;
- group members;
- topic logs;
- finance archive.

Импортируемые ID и значения, попадающие в HTML attributes, валидируются или безопасно экранируются. Неизвестное поле нельзя молча удалить, если оно может принадлежать поддерживаемой legacy-схеме.

#### DoD

- [ ] Finances, schedule и backup работают без DOM.
- [ ] Результаты fixture совпадают с baseline.
- [ ] Merge сохраняет все ссылки.
- [ ] Invalid backup не меняет активные данные.
- [ ] Перед replace существует recovery copy.
- [ ] Нет raw-вставки импортируемых строк в `innerHTML`.

### Этап 5 — надёжная cloud sync

#### Протокол

Для cloud row необходимы серверные metadata columns или эквивалентный RPC-контракт:

```text
user_id
data
schema_version
revision
updated_at
```

Сохранение использует compare-and-swap:

```text
UPDATE ...
SET data = next, revision = revision + 1
WHERE user_id = auth.uid()
  AND revision = expectedRevision
```

Операция должна быть атомарной на стороне PostgreSQL. Последовательность «сначала SELECT, затем обычный UPDATE» недостаточна.

#### Клиентские требования

Обязательный минимум (это и есть цель этапа):

- одновременно выполняется не больше одного save (последовательная очередь — уже реализована как `saveChain`);
- успешный ответ обновляет локальную base revision;
- ноль обновлённых строк означает conflict;
- network/RLS/server error не показывается как «Сохранено»;
- при конфликте автоматическая перезапись запрещена; выбор делает пользователь.

Достаточно и не расширять сейчас (см. §4):

- debounce остаётся простым объединением частых изменений (уже есть);
- offline: текущий snapshot остаётся в `localStorage` и отправляется при следующем изменении/`online`. Полноценная offline-очередь из нескольких snapshot'ов и сложный backoff не нужны — один ограниченный повтор достаточно.

Пользователь при конфликте может:

1. скачать локальный backup;
2. загрузить облачную версию;
3. после явного подтверждения заменить облако локальной версией.

Автоматический merge полного JSON между устройствами в рамках этого рефакторинга не выполняется.

#### Статусы UI

```text
loading / idle / dirty / saving / saved / offline / error / conflict
```

Статус должен быть доступен через `aria-live` и не исчезать автоматически при ошибке или конфликте.

#### DoD

- [ ] Save operations сериализованы.
- [ ] Conflict определяется атомарно на сервере.
- [ ] Более новая облачная revision не перезаписывается молча.
- [ ] Offline изменения сохраняются локально.
- [ ] Две вкладки и два браузера проверены отдельным сценарием.
- [ ] Logout завершает или отменяет ожидающий save до очистки session runtime.

### Этап 6 — UI-модули, доступность и выпуск

После стабилизации state и domain код страниц разделяется по владельцу поведения:

- dashboard;
- students/groups;
- schedule;
- payments;
- reports;
- settings/profile;
- общие dialog/modal/toast utilities.

Не требуется единый class-based lifecycle. Достаточно, чтобы модуль страницы владел своими DOM queries, rendering и event handlers и не обращался напрямую к Supabase или `localStorage`.

> **Статус реализации.** Полное page-разделение оставлено на 6.1 — отдельный будущий PR, потому что оно требует переписать 200+ строк inline event-handlers в `assets/app.js` (каждый handler мутирует общий `data`, вызывает 10–15 других глобальных функций и явно рассчитывает на classic-scope). Без Playwright/E2E-набора такой рефактор нельзя проверить безопасно; создание такого набора — отдельная работа (§4 «Не сейчас»). На Этапе 6 сделано то, что реально повышает выпускную готовность без риска: regression-guard тесты на a11y-примитивы (focus-trap, Escape, `aria-live`, отсутствие inline `on*` в HTML), актуализированный smoke-чеклист и release gate.

#### Минимальная доступность

Приоритет — **не сломать** уже работающее: focus-trap по `Tab` и закрытие по `Escape` в модалках уже есть в коде, их нужно сохранить при разделении файлов. Остальной список — best-effort по мере правок, а не блокер выпуска (a11y не про потерю данных). Полный a11y-аудит — отдельная инициатива при необходимости.

- `button`, `input`, `select` и `a` используются по назначению;
- у form controls есть label/accessible name;
- modal имеет dialog semantics;
- при открытии фокус переходит внутрь;
- Tab не уходит на фон;
- Escape закрывает допустимые modal;
- после закрытия фокус возвращается;
- dirty form требует подтверждения;
- toast и cloud status используют live region;
- видимый focus indicator сохраняется;
- учитывается `prefers-reduced-motion`.

Selective rendering вводится только там, где это упрощает код или решает измеримую проблему. Чистый полный render допустим.

#### Release gate

Перед каждым production deploy:

- lint и unit tests проходят;
- критический smoke проходит;
- legacy backup импортируется;
- fixture даёт прежние финансовые результаты;
- проверен вход и reload session;
- проверен cloud save и reload;
- проверена привязка owner marker;
- проверен гейтинг доступа (заблокированный/истёкший аккаунт не входит в кабинет);
- проверен экспорт backup;
- PR содержит риск и способ rollback.

После deploy вручную проверить вход, открытие ученика, сохранение занятия, оплату, reload и backup export.

#### DoD

- [ ] Нет одного глобального обработчика несвязанных feature areas.
- [ ] Page code не обращается к Supabase и storage напрямую.
- [ ] Основные сценарии доступны с клавиатуры.
- [ ] Light/dark theme и mobile layout сохранены.
- [ ] PNG-отчёт работает.
- [ ] CI гоняет lint и unit-тесты (жёсткий гейт «обязателен для merge» вводится только при появлении других контрибьюторов).
- [ ] README описывает запуск, тесты, deploy, данные и backup compatibility.

## 8. Общий Definition of Done

Рефакторинг завершён, когда одновременно выполнено следующее:

- [ ] Local state имеет owner marker, а mismatch блокирует upload.
- [ ] Cross-user RLS test проходит.
- [ ] Нет silent data loss при load, migration или import.
- [ ] Legacy backup поддерживается.
- [ ] Есть recovery path и rollback.

### Архитектура

- [ ] JavaScript использует содержательные ES Modules.

- [ ] Persistence не запускает rendering.
- [ ] Rendering не изменяет state.
- [ ] Нет override browser prototypes.

- [ ] Расписание не создаёт дубли.

## 9. Критерий остановки

После выполнения этой спецификации новые архитектурные инициативы автоматически не начинаются. Нормализация Supabase, новый framework, полный selective rendering и оптимизация больших наборов данных требуют отдельного подтверждённого запроса, измеримой причины и нового ADR.
