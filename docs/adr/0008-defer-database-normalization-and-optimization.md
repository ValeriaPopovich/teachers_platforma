# ADR-0008: Отложить нормализацию БД и преждевременные оптимизации

- Статус: Принято
- Дата: 2026-08-09

## Контекст

Первоначальный план включал переход от одного JSON blob к набору Supabase-таблиц, dual-write, runtime indexes, обязательный selective rendering и расширенный performance milestone. Эти инициативы значительно увеличивают объём и добавляют новые риски миграции, RLS, транзакций, offline sync и rollback.

Текущая главная проблема — безопасность и предсказуемость существующей модели данных, а не доказанное ограничение производительности JSON blob.

## Решение

Не включать в текущий рефакторинг:

- нормализацию Supabase;
- dual-write;
- realtime или field-level multi-device merge;
- repository API для каждой entity;
- обязательные runtime indexes;
- виртуализацию списков;
- полный selective rendering;
- смену frontend framework.

Эти работы могут быть предложены только после завершения текущей спецификации и при наличии измеримой причины: лимитов размера/скорости, требований серверной аналитики, collaborative editing или иной продуктовой потребности.

Новое предложение должно содержать актуальную data model, transaction boundaries, RLS для каждой таблицы, migration/rollback strategy, обработку удалений и отдельный ADR.

## Последствия

- Первый рефакторинг остаётся ограниченным и обратимым.
- Не требуется опасный dual-write двух источников правды.
- JSON blob остаётся текущей единицей cloud persistence.
- Возможные ограничения blob-модели принимаются до появления измеримого ущерба.

## Рассмотренные альтернативы

### Нормализовать Supabase параллельно с frontend refactoring

Отклонено: одновременно меняет слишком много границ и усложняет определение причины регрессии.

### Добавить indexes/selectors заранее

Отклонено: они создают вторичное runtime state без подтверждённой проблемы производительности.
