# ADR-0007: Минимальные feature-oriented модули

- Статус: Принято
- Дата: 2026-08-09

## Контекст

Первоначальный план задавал большую целевую структуру с десятками файлов, слоями и repository для отдельных сущностей. Для текущего объёма это может заменить один монолит множеством пустых или тесно связанных модулей.

## Решение

Модуль создаётся, только если у него есть самостоятельная ответственность, тестируемый контракт или собственный UI lifecycle.

Основные границы:

- bootstrap/config;
- auth/access;
- state/migrations;
- local persistence/cloud sync/backup;
- finances;
- schedule/lessons;
- feature pages;
- общие UI primitives.

Предпочитать feature ownership горизонтальному дроблению. Например, event handlers страницы учеников находятся рядом с её rendering, а финансовые расчёты — в отдельном DOM-free domain module.

Точная структура каталогов развивается вместе с кодом и не является acceptance criterion. Маленький модуль можно объединить с владельцем, если у него нет самостоятельного контракта.

## Последствия

- Меньше boilerplate и файлов-переадресаторов.
- Границы соответствуют реальным изменениям продукта.
- Структуру нельзя создать механически заранее; требуется оценивать ownership кода.
- При росте feature модуль можно разделить новым небольшим PR.

## Рассмотренные альтернативы

### Полная layered-структура с repository на каждую сущность

Отклонено для текущего JSON blob: создаёт интерфейсы, не соответствующие фактической единице хранения и транзакции.

### Оставить auth, domain и UI в одном `app.js`

Отклонено: критичные ответственности остаются нетестируемыми и связанными.
