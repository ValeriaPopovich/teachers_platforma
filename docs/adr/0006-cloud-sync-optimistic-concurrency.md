# ADR-0006: Серверная optimistic concurrency для cloud sync

- Статус: Принято
- Дата: 2026-08-09

## Контекст

Приложение сохраняет полный JSON одной строкой через Supabase `upsert`. Два устройства или две вкладки могут работать от одной версии и молча перезаписать друг друга. Debounce уменьшает число запросов, но не обеспечивает порядок и не обнаруживает конфликт.

## Решение

Cloud row содержит монотонную `revision`. Клиент хранит revision, на базе которой создан локальный state. Запись выполняется атомарным compare-and-swap на стороне PostgreSQL, через условный UPDATE или RPC:

```text
update only where user_id = auth.uid() and revision = expected_revision
```

При успехе сервер увеличивает revision. Если обновлено ноль строк, клиент переходит в состояние `conflict` и не перезаписывает cloud автоматически.

Клиент имеет одну последовательную save queue. Offline snapshots сохраняются локально. Пользователь при конфликте может скачать локальный backup, загрузить cloud или явно подтвердить замену cloud локальным состоянием.

## Последствия

- Более новая cloud version не теряется молча.
- Потребуется изменение текущего Supabase contract: колонка revision и/или RPC.
- UI должен различать saved, error, offline и conflict.
- Автоматический field-level merge не реализуется.

## Рассмотренные альтернативы

### `updated_at` и last-write-wins

Отклонено: timestamp не предотвращает перезапись и зависит от корректного протокола сравнения.

### SELECT revision, затем обычный UPDATE

Отклонено: между SELECT и UPDATE другое устройство может сохранить новую версию.

### Автоматический merge JSON

Отклонено: без модели операций и конфликтов может создать логически неконсистентные финансы и расписание.
