# Vue-архитектура и правила разработки

## Статус документа

Этот документ определяет целевую архитектуру Vue 3 и правила написания нового UI-кода.
Он применяется ко всему новому Vue-коду и к старому коду по мере миграции.

Подход адаптирован из `frontend-v2`: мы используем разделение на независимые пакеты,
доменные модули, публичные точки входа, сервисы и composables. Atomic Design, глобальная
регистрация компонентов, Nuxt-специфика и дробление простого компонента на отдельные
файлы шаблона, скрипта и стилей в этом проекте не применяются.

## Основные принципы

1. Проект организован вокруг бизнес-доменов: ученики, расписание, оплаты, отчёты и настройки.
2. Переиспользуемые инструменты не знают о бизнес-доменах и находятся в `packages`.
3. Vue-компоненты содержат только отображение и UI-логику.
4. Бизнес-операции выполняются сервисами, расчёты — доменными функциями и selectors.
5. Компоненты не изменяют store напрямую.
6. Зависимости направлены от приложения и модулей к пакетам, но не наоборот.
7. У каждой области есть явная публичная точка входа `index.js`.
8. Абстракция создаётся для подтверждённого повторного сценария, а не на будущее.

## Целевая структура

```text
packages/
  ui/                    # базовые визуальные компоненты
  icons/                 # единый реестр SVG-иконок
  styles/                # токены, reset, mixins и общие utilities
  use/                   # общие Vue-composables без бизнес-логики
  test-utils/            # общие фабрики и helpers для тестов

src/
  app/                   # запуск и композиция приложения
  modules/               # бизнес-модули
    dashboard/
    students/
    schedule/
    payments/
    reports/
    settings/
  domain/                # чистые бизнес-расчёты
  state/                 # store, persistence, migrations
  cloud/                 # внешняя синхронизация
  shared/                # временный legacy-слой во время миграции
```

`packages` пока являются локальными пакетами текущего репозитория. Выносить их в
отдельные npm-пакеты или настраивать публикацию не нужно. Независимость обеспечивается
границами импортов, публичными точками входа и архитектурными тестами.

## Назначение пакетов

### `packages/ui`

Содержит только универсальные компоненты без терминов предметной области.

Допустимо:

- `UiButton`, `UiModal`, `UiInput`, `UiBadge`;
- состояния `success`, `warning`, `danger`, `disabled`, `loading`;
- управление фокусом, клавиатурой и ARIA;
- визуальная и локальная UI-логика.

Недопустимо:

- `StudentCard`, `PaymentStatus`, `LessonForm`;
- импорт из `src/modules`, `src/domain`, `src/state` или `src/cloud`;
- прямое чтение store;
- вызов сервисов бизнес-модулей;
- сохранение данных и работа с Supabase.

Структура компонента:

```text
packages/ui/button/
  index.vue                    # декларативный шаблон компонента
  index.js                     # публичный экспорт
  scripts/
    index.js                   # props, setup и UI-логика
    constants.js               # только если вариантов действительно много
  styles/
    index.scss                 # стили компонента
  UiButton.test.js
```

Шаблон, логика и стили разделяются с первого компонента. `index.vue` не содержит
`<script setup>` и inline-стилей: он подключает `scripts/index.js` и `styles/index.scss`.
Дополнительные composables, constants и style partials создаются только при реальной
необходимости.

Публичный экспорт:

```js
// packages/ui/button/index.js
export { default as UiButton } from './index.vue';

// packages/ui/index.js
export { UiButton } from './button/index.js';
```

Использование:

```js
import { UiButton, UiModal } from '@ui';
```

Запрещены импорты внутренних файлов пакета из приложения:

```js
// Плохо
import UiButton from '../../packages/ui/button/index.vue';

// Хорошо
import { UiButton } from '@ui';
```

### `packages/use`

Общие composables с UI-поведением:

```text
useFocusTrap
useEscapeKey
useDisclosure
useBodyScrollLock
useClipboard
useMediaQuery
useFormFieldId
```

Composable находится в отдельной директории, если имеет тесты, константы или несколько
внутренних функций:

```text
packages/use/focus-trap/
  useFocusTrap.js
  useFocusTrap.test.js
  index.js
```

Правила:

- имя начинается с `use`;
- все слушатели снимаются в `onBeforeUnmount` или `onScopeDispose`;
- DOM используется только после `onMounted`, если нет гарантии существования элемента;
- composable возвращает минимальный публичный API;
- бизнес-термины в этом пакете запрещены.

### `packages/icons`

Содержит SVG-иконки и `UiIcon`. Компоненты не должны копировать одинаковый SVG.

```text
packages/icons/
  icons.js
  index.vue
  index.js
  scripts/index.js
  styles/index.scss
```

Иконка получает `name`, `size`, `label` и `decorative`. Пользовательские данные никогда
не передаются в `v-html`. Предпочтительны Vue-компоненты или контролируемый локальный
реестр SVG.

### `packages/styles`

Содержит дизайн-токены и общие низкоуровневые средства:

```text
packages/styles/
  tokens/
    colors.scss
    spacing.scss
    typography.scss
    radius.scss
    shadows.scss
    controls.scss
    motion.scss
  mixins/
    focus-ring.scss
    media.scss
    clickable-area.scss
    visually-hidden.scss
  index.scss
```

Пакет не содержит стили страниц, учеников или оплат. Стили бизнес-модуля остаются рядом
с модулем либо в его временном feature-SCSS до завершения миграции.

### `packages/test-utils`

Содержит только повторно используемые средства тестирования:

- `renderComponent` с общими настройками;
- фабрики состояния приложения;
- mock store и mock services;
- helpers для клавиатуры, модалок и времени.

Тестовая утилита добавляется после второго реального повторения.

## Структура бизнес-модуля

Atomic Design не используется. Компоненты группируются по назначению и домену.

```text
src/modules/payments/
  components/
    PaymentBalanceItem.vue
    PaymentHistoryItem.vue
    PaymentForm.vue
  composables/
    usePaymentFilters.js
    index.js
  payments.selectors.js
  payments.service.js
  PaymentsPage.vue
  index.js
```

Не нужно создавать пустые директории `composables`, `constants` или `components` заранее.
Они появляются только вместе с первым содержимым.

Публичный `index.js` модуля экспортирует только то, что разрешено использовать снаружи:

```js
export { default as PaymentsPage } from './PaymentsPage.vue';
export { createPaymentsService } from './payments.service.js';
```

Внутренние карточки и формы не экспортируются, пока другой модуль не получил обоснованный
сценарий их использования.

## Направление зависимостей

Разрешённый поток:

```text
app
  -> modules
     -> domain
     -> state через сервисы
     -> packages
  -> packages

cloud -> state
```

Правила:

- `packages/*` не импортируют `src/*`;
- `domain` не импортирует Vue, DOM, store, cloud и компоненты;
- компонент модуля может читать реактивное состояние через адаптер/composable;
- компонент вызывает сервис для изменения данных;
- сервис может использовать store и domain;
- selector только подготавливает данные для отображения и не изменяет состояние;
- один модуль не импортирует внутренний файл другого модуля;
- межмодульное взаимодействие идёт через публичный `index.js`, сервис или callback.

## Поток данных

```text
store -> selector/computed -> component props/template
user event -> named handler -> service -> store -> render
```

Компонент не должен делать так:

```js
store.update((draft) => {
  draft.payments.push(payment);
});
```

Правильно:

```js
function onPaymentFormSubmit(payload) {
  paymentsService.addPayment(payload);
}
```

## Граница UI-логики и бизнес-логики

### Бизнес-логика хранится в сервисах

Любая операция, которая меняет состояние предметной области или реализует бизнес-правило,
обязана находиться в сервисе модуля. Vue-компонент и его `scripts/index.js` только собирают
пользовательский ввод и вызывают публичный метод сервиса.

К бизнес-логике относятся:

- создание, изменение и удаление учеников, групп, занятий и платежей;
- изменение store и сохранение состояния;
- расчёт долгов, стоимости, абонементов и статусов оплаты;
- проверка конфликтов расписания;
- нормализация и преобразование бизнес-данных;
- координация нескольких domain-функций или нескольких изменений store;
- работа с persistence, backup, cloud и внешними API;
- принятие решения, разрешена ли бизнес-операция.

```js
// Плохо: бизнес-правило и изменение store внутри component script.
function onPaymentFormSubmit(form) {
  const amount = form.lessons * form.price;
  store.update((draft) => draft.payments.push({ ...form, amount }));
}

// Хорошо: component script делегирует операцию сервису.
function onPaymentFormSubmit(form) {
  paymentsService.addPayment(form);
}
```

Сервис может использовать store, domain-функции, selectors и инфраструктурные адаптеры.
Сервис не управляет DOM, CSS-классами, фокусом или состоянием раскрытия интерфейса.

### В component scripts находится только UI-логика

`scripts/index.js` отвечает за представление и взаимодействие пользователя с конкретным
компонентом.

К UI-логике относятся:

- props, emits и регистрация дочерних компонентов;
- подготовка классов и HTML/ARIA-атрибутов;
- локальные состояния `open`, `focused`, `loading`, `activeTab`;
- обработчики кликов, ввода и клавиатуры;
- управление фокусом, overlay и прокруткой;
- преобразование уже подготовленных данных в удобную view model;
- вызов сервиса или emit в ответ на пользовательское действие;
- подписка на внешний UI-источник с обязательной очисткой подписки.

Component script не должен:

- напрямую вызывать `store.update`, `store.replace` или persistence;
- дублировать domain-расчёты и selectors;
- выполнять запросы к Supabase или другому API;
- содержать правила начисления, оплаты, расписания или удаления связанных сущностей;
- обращаться к внутренним файлам другого бизнес-модуля;
- изменять DOM через `innerHTML`, `querySelector` или ручное создание элементов, если этим
  DOM-поддеревом владеет Vue.

### Крупная UI-логика выносится в composables

`scripts/index.js` остаётся точкой композиции компонента, а не местом для всей его
реализации. Самостоятельный кусок UI-поведения выносится в composable, если выполняется
хотя бы одно условие:

- логика имеет собственный жизненный цикл или очистку ресурсов;
- содержит несколько связанных `ref`, `computed`, `watch` и обработчиков;
- переиспользуется в двух компонентах;
- может быть протестирована независимо от шаблона;
- из-за неё основной `setup` перестаёт быстро читаться;
- отвечает за отдельную задачу: focus trap, фильтрация, клавиатурная навигация, form draft,
  clipboard, раскрытие списка или синхронизация с legacy bridge.

Структура:

```text
component/
  index.vue
  scripts/
    index.js
    composables/
      use-keyboard-navigation.js
      use-form-draft.js
      index.js
```

```js
// scripts/index.js — только композиция частей.
import { useFormDraft, useKeyboardNavigation } from './composables/index.js';

export default {
  setup(props, { emit }) {
    const { draft, resetDraft } = useFormDraft(props.modelValue);
    const { onListKeydown } = useKeyboardNavigation({ emit });

    return { draft, onListKeydown, resetDraft };
  },
};
```

Composable компонента содержит только UI-логику. Если в процессе выделения обнаруживается
бизнес-правило, оно переносится не в composable, а в service/domain/selector соответствующего
модуля.

Общий composable без бизнес-терминов помещается в `packages/use`. Composable, связанный с
учениками, оплатами или расписанием, остаётся внутри соответствующего бизнес-модуля.

## Правила Vue-компонентов

### Инструменты качества

- ESLint проверяет JavaScript и Vue Single-File Components;
- импорты в `.vue` и в `packages/**/*.js` сортируются `simple-import-sort`;
- порядок блоков SFC: `<script src>`, `<template>`, `<style src>`;
- пользовательские Vue-события именуются в `kebab-case`;
- Stylelint проверяет обычный SCSS и `<style lang="scss">` внутри `.vue`;
- Stylelint не требует BEM и не использует `b()`;
- TypeScript и связанные с ним lint-правила не подключаются;
- Prettier отвечает только за форматирование и не заменяет ESLint или Stylelint.

Legacy JavaScript не переводится на новые правила массовым автофиксом. Строгие правила
применяются к новому Vue-коду и `packages`, а старые файлы приводятся к ним при миграции.

### Общий формат

Для нового кода используется Composition API через внешний `scripts/index.js`.
`setup` всегда возвращает явный список значений, используемых шаблоном.

```vue
<script src="./scripts/index.js" />

<template>
  <button :disabled="isDisabled" @click="onButtonClick"><slot /></button>
</template>
```

```js
// scripts/index.js
import { computed } from 'vue';

export default {
  props: {
    /** Отключает интерактивность. */
    disabled: { type: Boolean, default: false },
  },
  emits: ['click'],
  setup(props, { emit }) {
    const isDisabled = computed(() => props.disabled);

    function onButtonClick(event) {
      emit('click', event);
    }

    return { isDisabled, onButtonClick };
  },
};
```

Правила декларативного шаблона:

- в атрибутах не используются тернарные операторы, `||`, `&&` и сборка объектов;
- классы, ARIA-атрибуты и набор атрибутов динамического элемента готовятся в `computed`;
- шаблон получает готовые значения: `buttonClasses`, `componentAttributes`, `isVisible`;
- допустимы простые `v-if`, `v-for`, вывод значения и вызов именованного обработчика;
- обработчики именуются по схеме `onElementEvent`, например `onSubmitButtonClick`;
- перечисления и варианты выносятся в `scripts/constants.js`;
- каждый prop сопровождается коротким JSDoc-комментарием.

### Props

- props описывают входные данные, а не команды;
- boolean называется положительно: `disabled`, `loading`, `open`;
- для перечислений используется validator или общая константа;
- объект и массив получают фабрику в `default`;
- компонент не изменяет prop;
- бизнес-сущность передаётся целиком, если компонент действительно отображает её как
  единую модель; иначе передаются только необходимые поля.

### Emits

- событие описывает произошедшее действие: `submit`, `close`, `select`, `delete`;
- обработчик именуется `onElementEvent`: `onSubmitButtonClick`, `onModalClose`;
- дочерний компонент не вызывает сервис родителя скрытно;
- для управляемого значения используется `v-model` и `update:modelValue`.

### Slots

Slot используется для структуры, которую базовый компонент не должен понимать:

```vue
<UiCard>
  <template #header>...</template>
  <template #default>...</template>
  <template #actions>...</template>
</UiCard>
```

Не добавляем десятки props для передачи фрагментов HTML. Если содержимое может быть
произвольным, нужен slot.

### Атрибуты

Базовый компонент должен корректно передавать `$attrs` на интерактивный корневой элемент.
Если корень неоднозначен, в component script задаётся `inheritAttrs: false`, а подготовленный
набор атрибутов передаётся в шаблон через `v-bind="componentAttributes"`.

### Вычисления и эффекты

- производное значение — `computed`, а не синхронизирующий `watch`;
- `watch` применяется для внешнего эффекта или синхронизации с не-Vue API;
- `watchEffect` не используется, если зависимости и причина эффекта могут быть названы явно;
- глобальные слушатели, таймеры и observers всегда очищаются;
- тяжёлые расчёты остаются в domain/selectors, а не в шаблоне.

### Безопасность

- пользовательский HTML не выводится через `v-html`;
- внешние URL проходят существующую проверку `safeExternalUrl`;
- текст по умолчанию выводится интерполяцией `{{ value }}`;
- destructive-действие требует подтверждения;
- секреты и ключи не хранятся во frontend-коде.

## Базовые UI-компоненты первой очереди

Компоненты создаются по мере миграции, но их целевой первый набор зафиксирован:

```text
UiIcon
UiButton
UiIconButton
UiBadge
UiCard
UiSectionHeader
UiEmptyState
UiFormField
UiInput
UiTextarea
UiSelect
UiCheckbox
UiSwitch
UiTabs
UiProgress
UiModal
```

Сначала реализуются:

1. `UiIcon`, `UiButton`, `UiIconButton`;
2. `UiBadge`, `UiCard`, `UiSectionHeader`, `UiEmptyState`;
3. `UiFormField`, `UiInput`, `UiSelect`;
4. `UiTabs`, `UiProgress`;
5. `UiModal` и необходимые ему composables.

Новый базовый компонент создаётся, если выполняется хотя бы одно условие:

- есть два реальных места использования;
- компонент инкапсулирует сложное доступное поведение;
- компонент задаёт единый критичный контракт, например кнопка или поле формы.

Нельзя создавать универсальный компонент только потому, что похожий HTML теоретически
может появиться позже.

## Стили компонентов

- базовый компонент использует токены `packages/styles`;
- стили по умолчанию локальны для компонента;
- глобальные классы разрешены только для reset, токенов и временной совместимости с legacy;
- inline-стили запрещены, кроме вычисляемых значений вроде ширины progress;
- состояния `hover`, `focus-visible`, `disabled`, `loading` проектируются одновременно;
- минимальная зона нажатия интерактивного элемента — 44 на 44 CSS-пикселя там, где это
  возможно без нарушения плотности интерфейса;
- анимация учитывает `prefers-reduced-motion`;
- компонент проверяется в светлой и тёмной теме.

## Доступность

Для каждого компонента проверяются:

- корректный семантический HTML;
- доступное имя интерактивного элемента;
- управление только клавиатурой;
- видимый `focus-visible`;
- состояния `aria-expanded`, `aria-selected`, `aria-invalid` и `aria-describedby`;
- возврат фокуса после закрытия модального окна;
- закрытие overlay по Escape, если это не разрушает данные;
- `aria-live` для toast и динамических статусов.

Кликабельный `div` запрещён. Используется `button` или `a`.

## Тестирование

### Базовый UI-компонент

Тестирует публичный контракт:

- рендер default-состояния;
- варианты и размеры, если они влияют на поведение;
- disabled/loading;
- события;
- `v-model`;
- slots;
- клавиатуру и ARIA для сложных компонентов.

Не тестируются внутренние refs, имена приватных функций и точный набор внутренних тегов,
если это не часть доступного контракта.

### Компонент бизнес-модуля

Тестирует:

- отображение подготовленных данных;
- пустое, нормальное и ошибочное состояния;
- вызов сервиса или emit с правильными аргументами;
- отсутствие прямого изменения store.

### Обязательные проверки перед коммитом

```bash
npm run check
npm run build
```

Для затронутого пользовательского сценария запускается соответствующий Playwright-тест.

## Правила миграции legacy UI

1. Переносится один законченный UI-срез.
2. Существующие domain, selectors и services сохраняются, если их контракт достаточен.
3. Сначала создаётся Vue-компонент, затем переключается точка монтирования.
4. Старый `innerHTML` и обработчики удаляются только после прохождения тестов.
5. Vue и legacy не должны одновременно владеть одним DOM-поддеревом.
6. Временное взаимодействие выполняется через явный адаптер или событие с описанным payload.
7. После переноса модуля его временные события удаляются в пользу props/emits/composables.
8. Миграция не должна одновременно менять бизнес-правила и визуальный контракт без
   отдельной причины и тестов.

## Что мы намеренно не переносим из `frontend-v2`

- Atomic Design и директории `atoms/molecules/organisms/templates`;
- глобальную регистрацию большого числа компонентов;
- Nuxt/SSR/WebView-слои;
- центральный service locator;
- создание всех возможных директорий в каждом модуле;
- Storybook до появления устойчивого базового UI-набора;
- монорепозиторную сложность и публикацию локальных пакетов.

## Критерии готовности компонента

Компонент готов, когда:

- находится в правильном слое;
- имеет минимальный и понятный публичный API;
- не содержит бизнес-логики, если это базовый UI-компонент;
- не изменяет store напрямую;
- использует токены, а не случайные значения без причины;
- доступен с клавиатуры;
- очищает созданные эффекты и слушатели;
- покрыт тестами пропорционально риску;
- экспортирован через ближайший `index.js`;
- проходит lint, unit-тесты и production build.
