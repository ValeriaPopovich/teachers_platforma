# Включение серверного CAS для cloud sync

Клиент уже использует `src/cloud/sync-protocol.js` и `src/cloud/supabase-adapter.js`; обычного `upsert` для `app_data` больше нет. До обновления базы приложение безопасно загружает существующую cloud row, но блокирует cloud write и показывает пользователю понятный статус «Изменения пока сохраняются только на этом устройстве».

Read-only REST-проверка 2026-08-09 подтвердила текущее состояние live-проекта: PostgreSQL вернул `42703: column app_data.revision does not exist`.

## Единственный шаг

Supabase Dashboard → SQL Editor → New query → вставить содержимое [`supabase/migrations/2026_stage5_add_revision_cas.sql`](../supabase/migrations/2026_stage5_add_revision_cas.sql) → Run.

Миграция:

- добавляет `revision integer not null default 1` и `schema_version integer not null default 1`;
- создаёт authenticated RPC `save_app_data(p_data, p_expected_revision, p_schema_version)`;
- обновляет строку только при совпадении expected revision;
- идемпотентна; rollback записан в комментарии файла.

После Run достаточно обновить страницу — дополнительный diff или deploy клиентского кода не нужен.

## Проверка

1. Изменить данные: статус должен перейти `Сохраняем…` → `Сохранено`.
2. Перезагрузить страницу и проверить изменение.
3. Открыть две вкладки. Изменить первую, затем вторую: во второй остаётся сообщение «На другом устройстве есть более свежие изменения».
4. Проверить три действия: скачать копию с этого устройства, открыть данные с другого устройства или оставить данные с этого устройства. Последнее требует явного подтверждения и всё равно использует CAS.

До успешного Run не пытайтесь возвращать legacy `upsert`: блокировка записи намеренная и защищает более новую копию от молчаливой перезаписи.
